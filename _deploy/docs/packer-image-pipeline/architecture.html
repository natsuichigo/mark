    Architecture

    How the repository is organised, and the two build shapes it uses.

    Two Build Shapes on AWS

    Two-stage (Linux)

    • Stage 1, amazon-ebssurrogate, builds the disk from scratch so the OS gets a custom, CIS-compliant partition layout.
    • Stage 2, amazon-ebs, starts from that base AMI and configures, hardens and validates it.
    • Two manifests: manifest-aws-base.json and manifest-aws-final.json.

    Single stage (Windows)

    • Starts from the vendor AMI and only configures it, because no custom partitioning is needed.
    • The credential change is the last provisioner, with skip_clean = true, so Packer does not try to clean up using a password it just replaced.
    • One manifest: manifest-aws-final.json.

    On vSphere, Linux builds boot from a kickstart ISO and Windows from an autounattend ISO, and the result is published to a content library as a template.

    Pipeline Shape

    .github/workflows/<os>-golden-image.yml        # WHEN to build: triggers, inputs, job env
  └── .github/actions/build/<family>-golden-image  # HOW: orchestration
        ├── packer/setup-tools                     # tools and plugins
        ├── packer/build-with-validation           # init / validate / build
        ├── aws/validate                           # optional post-build EC2 test
        ├── aws/ami-cleanup                        # retention, once per name prefix
        └── (summary is a separate job)
    • Workflows hold no build logic: triggers, inputs, environment and job definitions only.
    • packer/build-with-validation is shared by every OS family and is never forked, so the init/validate/build and manifest-parsing logic exists once.
    • The summary is its own job with if: always(), so it publishes even when a build fails.
