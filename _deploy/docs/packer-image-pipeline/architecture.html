    Architecture

    How the repository is organised, how a vSphere build is shaped, and where it runs.

    Where It Runs

    1
    GitHub ActionsA push or a manual run queues jobs for runs-on: platform-lab-packer
    ↓
    2
    Platform Lab clusterThe ARC listener picks the job up over outbound HTTPS and starts an ephemeral runner pod
    ↓
    3
    vCenterPacker creates the build VM through the vSphere API
    ↓
    4
    Build VMPacker and Ansible connect over SSH (Linux) or WinRM (Windows), harden and validate it
    ↓
    5
    Content libraryThe template is published; old versions beyond the retention count are removed

    Every connection starts from the runner pod. The kickstart and autounattend files go into the VM on a CD (common_data_source = "disk"), not over Packer's built-in HTTP server, so the VM never has to reach back into a pod sitting behind WSL's NAT. That is what lets a laptop cluster drive the builds. The runner pods have no Kubernetes API rights, because Packer never touches the cluster.

    Two Builds on vSphere

    RHEL 8.10

    • vsphere-iso boots the install ISO and reads a kickstart from an attached CD.
    • The VM registers with Red Hat Subscription Manager during the build, then Ansible applies the CIS role.
    • Packer connects as an ephemeral build user over SSH.

    Windows Server 2022

    • vsphere-iso boots the install ISO with an autounattend file and init scripts on a CD (cd_files).
    • VMware Tools and WinRM are set up at first boot, then Ansible applies the baseline over WinRM.
    • CIS for Windows is left to GPO after domain join.

    Both publish to a vSphere content library as a template.

    Pipeline Shape

    .github/workflows/<os>-golden-image.yml        # WHEN to build: triggers, inputs, job env
  └── .github/actions/build/<family>-golden-image  # HOW: orchestration
        ├── packer/setup-tools                     # Packer, plugins, govc
        ├── packer/build-with-validation           # init / validate / build
        ├── vmware/content-library-cleanup         # retention
        └── (summary is a separate job)
    • Workflows hold no build logic: triggers, inputs, environment and job definitions only.
    • packer/build-with-validation is shared by every OS family and is never forked, so the init/validate/build and manifest-parsing logic exists once.
    • The summary is its own job with if: always(), so it publishes even when a build fails.
    • Runner labels come from repository variables (RUNNER_LABELS_SMALL, RUNNER_LABELS_LARGE), so pointing the pipeline at the lab's runners is a settings change, not a code change.
