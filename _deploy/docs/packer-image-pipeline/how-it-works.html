    How It Works

    One build, from a workflow run to a published, validated vSphere template.

    1
    TriggerA push to dev touching that OS's build files, or a manual run choosing the environment (dev / prd) and how many templates to keep
    ↓
    2
    ResolveA small job works out the image version and run parameters, and rejects bad values before Packer starts
    ↓
    3
    BuildA runner pod in the Platform Lab cluster runs Packer against vCenter; Ansible configures and hardens the VM
    ↓
    4
    Validate inlineThe OS's validator runs as the last provisioner before clean-up. Any failure aborts the build
    ↓
    5
    Publish and tidyThe template goes to the content library; govc removes versions beyond the retention count
    ↓
    6
    SummariseA separate job publishes the run summary, even on failure

    Runs of one workflow on one branch never overlap: concurrency queues them, with cancel-in-progress: false, because cancelling mid-build would leave an orphaned VM behind in vSphere.

    Validation Inside the Build

    Each OS has a validator in tests/: validate-rhel-image.sh and validate-windows-image.ps1. They print records in a shared vocabulary that the summary action understands:

    Record Example
    Section header ━━━ Operating System ━━━ or --- Operating System ---
    Check PASS : Password max days <= 365, with FAIL, WARN, SKIP or INFO
    Benchmark 🔧 Disk write speed: …
    Summary A closing block with Passed:, Failed: and Warnings: counts

    One summary parser handles every OS family, so adding an OS means emitting the same records, not writing a new parser.

    Running on the Lab's Runners

    The repo's runner labels are variables, so moving the builds into the lab needed no workflow changes:

    RUNNER_LABELS_SMALL = ["platform-lab-packer"]
RUNNER_LABELS_LARGE = ["platform-lab-packer"]

    The scale set has a maximum of two pods, so a build and its small resolve and summary jobs can overlap, and zero pods while idle. Each pod installs its tools at the start of the job: Packer and govc at pinned versions (1.16.0 and v0.56.0), then the plugins and ansible-core.

    Credentials and Security

    • Nothing sensitive is committed. vCenter, build-account and Red Hat subscription credentials come in as GitHub secrets and reach Packer as PKR_VAR_* environment variables.
    • The build account is ephemeral and rotated freely.
    • Known limitation, Windows on vSphere: Packer shuts the VM down over WinRM as Administrator, so the template still carries the build password on that account. It is reset at deployment, in the vSphere customization spec.
    • The runner pods can't touch the cluster. They run under a ServiceAccount with no permissions and no mounted token.

    Building Locally

    Validation needs no vCenter connection:

    packer init builds/vmware/linux/rhel/8.10
packer fmt -check -recursive builds/
packer validate \
  -var-file=builds/vmware/vsphere.pkrvars.hcl \
  -var-file=builds/vmware/common.pkrvars.hcl \
  -var-file=builds/vmware/linux-storage.pkrvars.hcl \
  -var-file=builds/vmware/linux/rhel/8.10/linux-rhel.pkrvars.hcl \
  -var image_version=20260101-test \
  builds/vmware/linux/rhel/8.10
