    The Claude Skills

    md-to-docs and docs-to-deck: Markdown in, case-study pages and slide decks out.

    The authoring tools are two Claude Code skills committed in the repo under .claude/skills/. A skill is a folder with a SKILL.md that tells Claude Code when and how to use it, plus the scripts it runs. Because they are in the repo, there is nothing to install: clone it, open Claude Code in the folder, and the skills are available. The scripts also run on their own with plain python3.

    md-to-docs: Markdown to a Case-Study Page

    1
    Scaffold the projectscaffold_project.py creates docs/<project>/, its CSS, its index page and a starter _src/docs.config.json
    ↓
    2
    Write the MarkdownOne file per page in _src/, plus one nav[] entry per page in the config
    ↓
    3
    Build the setbuild_project.py --project <project> regenerates every page
    ↓
    4
    Validatevalidate_pages.py --project <project> before committing

    A page's Markdown starts with a title and a one-line subtitle, then ordinary ## sections:

    # Architecture
The repo layout, the two kinds of page, and which files are generated.

## The Repository
...

    md_to_page.py wraps that in the full page: header, sidebar, table of contents, previous/next links and footer. Source files can also be PDFs: pdf_to_md.py converts them to Markdown first, for review before publishing.

    The sidebar is baked into every page. Adding, removing or reordering a page changes the sidebar on all of them, so build_project.py always rebuilds the whole set, never one page.

    What the validator checks

    Structure
    All pages share one sidebarExactly one active linkUnbroken prev/next chainPage skeleton intact
    Links
    Same-set .html links resolveRelative CSS/JS/images resolve
    Rendering
    No unrendered Markdown tablesNo literal code spansClean subtitles
    Hygiene
    Tags balancedEvery page has a Markdown source

    Every case study has the same shape

    Page What it covers
    Overview The problem, what I built, the stack, a link to the repo
    Architecture The main components and how they fit together
    How It Works The pipeline or workflow, step by step
    Lessons & Next Steps Trade-offs, what I would change, what comes next

    docs-to-deck: Case Study to Walkthrough Deck

    The second skill builds a reveal.js walkthrough deck from a project's published case-study pages, so the slides and the pages tell the same story.

    1
    Pick the audienceoverview for a recruiter, deep-dive for a technical interview, talk for a meetup
    ↓
    2
    Gather the factsdeck_facts.py lists the project's pages and an agenda shaped by the deck type
    ↓
    3
    Write a deck planJSON: slides as declared blocks; scaffold_deck.py renders them into the house components
    ↓
    4
    Validate and lookvalidate_deck.py checks structure; screenshot_deck.py renders every slide in Playwright and measures overflow

    Why render screenshots? A slide that overflows still passes every structural check. The only reliable test is to render each slide at real viewport sizes and measure it, so the skill does exactly that.
