    Architecture

    One laptop, one node, and Git deciding what runs on it.

    1
    WorkstationFedora 44 on WSL 2, VS Code, Podman, kind, kubectl, Helm, k9s; QEMU/KVM, libvirt and Vagrant for VM images
    ↓
    2
    ClusterA single kind node on Podman, created by bootstrap/cluster-up.sh
    ↓
    3
    GitOpsArgo CD, the only hand-installed chart, syncs everything in kubernetes/argocd/apps/
    ↓
    4
    PlatformTraefik, Metrics Server, Headlamp, a container registry, GitHub runners; profiles for Prometheus/Grafana, AWX and Backstage

    The GitOps Flow

    A single root Application points at a folder of child Applications (the app-of-apps pattern). Each child pulls a pinned chart from upstream and its values from this repo. Sync waves bring the platform up in order:

    0
    Wave 0Traefik, Metrics Server, platform-config (namespaces, quotas, RBAC)
    ↓
    1
    Wave 1Actions Runner Controller, Headlamp (the cluster UI), the lab registry
    ↓
    2
    Wave 2One runner scale set per repo: platform-lab and platform-lab-packer
    ↓
    3
    Wave 3Whichever heavy profile is switched on

    Runners Inside the Cluster

    A workflow job with runs-on: platform-lab is picked up by the ARC listener, which long-polls GitHub over outbound HTTPS. The controller then starts an ephemeral runner pod, which runs the job and is deleted. Because the connection is outbound only, it works from behind WSL's NAT, and with a minimum of zero runners nothing runs while idle. The runner pod's ServiceAccount has the read-only view role.

    My GitHub account is personal, not an organization, and GitHub only lets a personal account register runners per repository. So each repo that uses the lab gets its own scale set: one Argo CD Application and one values file, sharing the same GitHub App. The Packer pipeline has its own set, platform-lab-packer, whose pods get no Kubernetes API rights at all.

    Where Each Kind of Job Runs

    Job Runs on Why
    Packer image builds In-cluster runners (platform-lab-packer) Packer drives vSphere remotely, so the pod only makes outbound connections and needs no KVM or Docker
    Ansible EE and Backstage image builds GitHub-hosted runners, pushing to a registry Container builds would need privileged Docker-in-Docker pods
    Platform health checks, Ansible against the lab In-cluster runners They need to reach the cluster
    Terraform for the lab and GitHub settings In-cluster runners, apply behind an approval Close to the cluster, and a required reviewer gates every apply

    Rule of thumb: container builds run on GitHub's machines, and jobs that drive something in the lab (the cluster, or vSphere for Packer) run on my runners, so runner pods never need privileged mode.

    Reaching the UIs

    Every UI is an Ingress on Traefik at <name>.platform-lab.localhost. kind has no cloud load balancer, so Traefik's Service is a NodePort fixed at 30080. The kind cluster definition maps 127.0.0.1:80 on the laptop to that port, so the UIs are up whenever the cluster is, with no port-forward to keep running. Names ending in .localhost resolve to loopback, and the mapping listens on loopback only, so nothing is reachable from the network.

    browser ─► 127.0.0.1:80 ─► kind node :30080 ─► Traefik ─► Ingress host ─► Service
           # kind extraPortMappings      # NodePort            # argocd, headlamp, grafana, ...

    Headlamp is the cluster UI: workloads, logs, events, a shell into pods and YAML editing. It has no login: it acts as its own cluster-admin ServiceAccount, so access is decided by who can reach it. A Traefik IP allow-list admits only requests that came in through the laptop's port mapping, and a NetworkPolicy lets only Traefik connect to the pod. Both were tested from a pod: 403 through Traefik, a timeout when called directly.

    Where Images Live

    Kind Built where Stored where
    Ansible EEs for AWX GitHub-hosted runners, or locally with Podman The lab registry (zot), at registry.platform-lab.localhost/<name>:<tag>
    VM images In WSL with Packer's qemu builder on KVM; tested with Vagrant qcow2 files and Vagrant boxes on the laptop
    vSphere templates The Packer pipeline, on the lab's runners The vSphere content library

    One registry name works from both sides. From WSL, the name resolves to loopback and goes through the kind port mapping and Traefik. Pods are pulled by containerd on the node, which sits outside cluster DNS, so a hosts.toml on the node points the same name at the registry's fixed ClusterIP. A push from the laptop and a pull from AWX use one image reference.

    KVM inside WSL. WSL 2 runs a real Linux kernel with nested virtualization, so /dev/kvm is there. Packer's qemu builder installs an AlmaLinux 9 image from a kickstart on a CD, validates it inside the build, and writes a qcow2 disk and a Vagrant box. No Hyper-V VM, VirtualBox or cloud account is involved.

    Security Layers

    GitHub never connects in: the runner listener long-polls out over HTTPS, so there are no open ports. The threat model is about who can run code on the runners and what that code can reach:

    Risk Control How it's tested
    Someone else triggers a job Fork PRs need approval; only approved actions; read-only default token Repo settings; the health workflow still passes
    A trusted action is hijacked Actions pinned to commit SHAs, Dependabot keeps them current grep uses: shows only SHAs
    Job code escapes its pod Non-root runners; namespace enforces Pod Security restricted A privileged pod mounting the node's disk is refused
    Job code attacks the platform NetworkPolicy: DNS, HTTPS to the internet and the API only; read-only RBAC Before/after reachability test from a test pod; kubectl auth can-i
    Job code steals credentials No Secrets mounted in job pods; the GitHub App key stays with the listener Inspect a live runner pod's volumes
    Infrastructure changed by mistake Terraform applies wait for a required reviewer Environment protection rule

    Capacity model

    • Core, always on: kind node, Argo CD, Traefik, Metrics Server, Headlamp, the registry, ARC. About 1.5–1.8 GB, plus runner pods only while a job runs.
    • One heavy profile at a time: observability ~1.0–1.4 GB, AWX ~1.5–2.0 GB, Backstage ~0.6–1.0 GB.
    • Every chart sets requests and limits; container builds that need lots of memory run on GitHub-hosted runners instead. A 2 GB VM build in WSL means switching the heavy profile off first.
